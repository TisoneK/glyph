Session 1 of the current office (Kofi, S001). Two things were asked for: the
user's target (`https://cryptonichub.pro`), and — after a protocol failure

## 1. The failure that started it

`sh .context/core/bin/context-sync verify` reported 20 core files as FAILED on
this Windows machine, and told the agent the core "does not match its
manifest — do not fix it in place; run rollback". The ledger was innocent:

- the manifest hash for a failing file equalled the **LF blob** hash exactly
  (`roles/docs-agent.md`: `c37872b5…` both from `git show HEAD:` and from
  `MANIFEST.sha256`), while the worktree file hashed to `3cc12030…` — CRLF;
- `git status` reported the tree **clean** and `git checkout -- <path>` was a
  silent no-op (stale stat cache — git never re-hashed the CRLF copies);
- deleting the files and re-checking them out restored LF and `verify`
  reported `core OK`.

So: the ledger was correct, the checkout was not, and the tool's diagnosis
("hand-edited core") pointed the wrong way. Both halves are logged upstream in
`memory/office/flaws/log.md` (2026-09-23) — the misleading diagnostic, and the
two `.ps1` ports that make `verify` fail on Windows regardless.

Version facts: vendored core **0.8.0**, package upstream **2.0.3** (the user's
"is it at v2.x.x?" — yes).

## 3. Upstream defects found and reported

1. **`ledger-state.ps1` cannot be parsed by any PowerShell engine.**
   Line 60 interpolates a label inside a double-quoted string
   (`"^\s*[-*]\s*\*\*$Label:\*\*\s*(.*)$"`) — `.NET`'s parser reads `$Label:` as
   a scope-qualified variable and errors in 5.1 *and* 7. `ledger-mem.ps1` also
   fails 5.1 parsing. Because `ledger-sync`'s `parse_ports` runs the ps1 ports
   through the engine it finds first (`powershell` 5.1 on any Windows box, even
   when `pwsh` is installed), `verify` exits 3 on Windows and **every gate that
   calls it fails** — while `verify_tree` (the manifest check) passes.
2. **A CRLF-only mismatch is diagnosed as tampering.** `verify` says "core does
   not match its manifest … do not fix core in place; run rollback" for what is
   purely a line-ending difference in the working tree. Suggested fix: detect
   the EOL-only case (compare with CR removed) and say so.

Both are in `memory/office/flaws/log.md` for upstream harvest, with the local
workaround in `memory/overrides/rules.md` (`[core-defect]`): treat
`sha256sum -c MANIFEST.sha256` inside `core/` plus the sh-port parse as the
integrity gate until the package ships a fix.

## 4. cryptonichub.pro — what the capture actually shows

**What the target is.** A Cloudflare-fronted Next.js (App Router, turbopack
chunks) site — a landing page plus `/login` and `/register`. Nothing else is
reachable without an account.

**Capture** (live Playwright, three page loads accumulated into one target,
234 flows / 22 endpoints / 20 fields):

- Every byte of non-static traffic is infrastructure: the Cloudflare RUM
  beacon (`POST /cdn-cgi/rum`, `cdn-cgi/rum`, `/_rsc` prefetches of `/login`,
  `/register`, `/`), Google Fonts, and `static.cloudflareinsights.com`.
- **No JSON API surface is exposed unauthenticated** — 0 dictionary entries,
  0 rosetta decodings, because no API responses were ever fetched. The app's
  data layer sits behind the login wall (and, per the SNI candidates, plausibly
  on hosts that are not linked from the landing page).

**Sensitive findings, before and after the fix:** 11 findings (1 critical,
3 high) → **9 (0 critical, 2 high)**. The two remaining high findings are
`auth_endpoint` on `/login` and `/register` — true by construction, not
exposures. The medium/low tail is SNI bug-host candidates on Cloudflare shared
IPs; note that on a Cloudflare-fronted target the score is inflated by
wildcard certs and large shared-IP sibling sets, which is expected rather than
suspicious (parked as a calibration question).

**The false positive that mattered:** `secret_token` in `$.siteToken` of
`POST cryptonichub.pro/cdn-cgi/rum`, which `risk.py` then escalated to CRITICAL
`unauthenticated_sensitive_data` ("returns sensitive data with no
authentication observed"). The value is the Cloudflare Web Analytics **site
tag** — published in the page's own HTML for the beacon. A detector that
reports the site's own analytics tag as a leaked credential costs an analyst
real time on a live target, so it was fixed rather than parked.

## 5. Product changes

1. **`fix(sensitive)`** — `glyph/sensitive/detectors.py` gained
   `_PUBLIC_IDENTIFIER_NAMES = {"sitetoken", "site_token"}` and the generic
   secret rule now skips those names. The exception is deliberately narrow
   (a test asserts `sessionToken` and `siteApiToken` still flag). Proven on the
   live catalog, not only in tests: re-running `glyph sensitive` on the capture
   dropped the critical and the false secret while keeping every genuine
   finding (11 → 9).
2. **`chore(repo)`** — the root `.gitattributes` now carries
   `* text=auto eol=lf`. Windows worktrees had been holding CRLF copies of
   tracked files whose blobs were LF; git treats those as clean until the file
   is edited, and then the whole file diffs and `git diff --check` (an exit-gate
   check) fails on every line — exactly what happened to `detectors.py`. No
   blob content changed.
